# V2.1 Integration Contract

This reference describes how `private-reading-guide` should connect to the V2.1 knowledge-ingestion workflow. It is an interface contract, not an instruction to migrate old V1 data.

## Inputs

### source_record

Provides:

- `source_id`
- `canonical_work_id`
- work title and authors
- document role
- release context
- completeness
- provenance
- source reading status
- bibliographic verification status
- content fact-check status
- evidence scope

Use it to understand what material is actually in hand. Do not use it as a substitute for the source's argument.

### authorized_sources

Primary writing basis.

At minimum bind:

- `asset_id`
- `extraction_id`
- actual authorized text/range
- output hash when available

The guide should read the authorized ExtractedSource itself before relying on old synthesis.

### reading_coverage

Record what was actually read:

- text coverage;
- figures read / not read / partial;
- tables read / not read / partial;
- representation used for visual reading when applicable.

Never infer reading from preservation status.

### curation_data

Auxiliary input only.

Useful fields include:

- claims
- evidence
- value_assessment
- gaps
- review_summary
- previous guide-generation metadata

Rules:

- Source statements in curation must still be checked against authorized ExtractedSource.
- Interpretation may help organize prose but must remain distinguishable.
- CurationData never becomes primary evidence merely because it is structured.

### reader_context

Use only explicit user context. Do not infer personal interests or goals from unrelated history inside the skill.

### style_rules

Apply the current final-prose rules, including:

- no empty contrast templates;
- no process residue;
- concentrated limitations;
- continuous prose;
- neutral handling of partial numbers;
- no fixed theme count for short material.

## Outputs

### guide_markdown

Long-term human-readable guide.

Characteristics:

- continuous prose;
- sparse headings;
- source-grounded;
- readable independently of system logs;
- no cloud/staging/hash/task internals.

### evidence_links

Map guide paragraph IDs or stable blocks to evidence IDs / source locations.

Only use locator precision actually available.

Do not invent:

- PDF page mapping;
- bbox;
- line numbers;
- figure details.

### unresolved_issues

Keep only issues that materially affect reading, attribution, or later use.

Examples:

- full text unavailable;
- extraction phrase uncertain;
- figure not visually read;
- bibliographic field needed for formal citation.

Do not copy every runtime warning.

### coverage_statement

A short factual statement of what the guide actually read.

Example:

> 已读当前版本的全部提取文字；三张提取图片已保存，未进行视觉识读。

Do not imply the canonical full work was read when only an abridged version was available.

## Evidence behavior

Recommended evidence order for guide generation:

1. SourceRecord for identity/range.
2. ExtractedSource for source claims.
3. Visual observations for actual image interpretation.
4. CurationData for organization and derived understanding.
5. Cross-reading material when explicitly authorized.

ReadingGuide is derivative. It does not become the first-level evidence source for later factual answering.

## Human Preview boundary

The Skill may provide the guide prose and coverage statement. The surrounding workflow owns:

- title/author/source header rendering;
- conversion status when needed;
- material status when needed;
- image-policy choice UI when needed;
- human confirmation controls;
- staging/cloud/archive operational messages.

Normal Human Preview should not display:

- source staging state;
- cloud archive queue;
- hashes;
- internal paths;
- task IDs;
- Feishu file keys;
- process logs.

## Verification behavior

Normal guide generation does not automatically perform external fact-checking.

External bibliographic verification is triggered only by the surrounding workflow or explicit user request, such as:

- formal citation;
- internal source conflict;
- a critical missing bibliographic field;
- canonical-work matching;
- explicit verification request.

Content fact-checking is separate and only runs when explicitly requested.
